## How to read this report

- **Confidence on every row is "read code only"** unless a row says otherwise. Nothing was run, no browser session was driven, and **the MongoDB database was not queried**. Anything that lives in database content (service names, service prices, the current `paymentsettings` document, existing user/booking data) is marked UNSURE and listed in "Data I need from you" below.
- Status legend: MATCHES · PARTIAL · DIFFERENT · NOT BUILT · UNSURE (as defined in the audit brief).
- Paths are relative to the repo root. `bookingRoutes.js` = `server/routes/bookingRoutes.js`. Line numbers are from the working tree as it was on audit day.
- A UI element with no server-side enforcement is rated PARTIAL, per the rules of evidence.

## Chapter 1.6 Definition of Terms

| T1 | Statuses: Pending, Scheduled, In Progress, Completed, Cancelled, Rescheduled | DIFFERENT | `Booking.js:53-57` | **Real enum: `['Pending','Approved','In Progress','Completed','Cancelled']`** (default `Pending`). **No "Scheduled" (the equivalent is `Approved`) and no "Rescheduled" status.** Rescheduling is sub-state: `rescheduleRequest.status` (`None/Pending/Approved/Denied`) and `disruption.status` (`None/Reported/Rescheduled`). **Pending** = awaiting admin approval + technician assignment; customer can change date/time directly while Pending. **Approved** = admin approved (technician required). **In Progress** = set by admin button or by cron on/after the scheduled date. **Completed** = admin "Mark Completed" or technician report submission; not triggered by payment. **Cancelled** = customer or admin cancel (opens refund if DP on file). **Transitions:** UI offers Pending→Approved→In Progress→Completed plus Cancel from any non-final; **server `admin-update` accepts any enum value from any non-Cancelled state with no transition validation** (e.g. Pending→Completed, Completed→Pending); disruption-reschedule sets In Progress→Approved; admin deleting a report sets Completed→In Progress (`reportRoutes.js:316-323`); Cancelled is terminal. |

# 5. Top mismatches the paper must change (ordered by how visible in a demo/defense)

1. **Senior Citizen/PWD discount** (S7h): a "PWD/Senior Citizen" upload box is on the payment dialog, but the file is thrown away and no discount is ever applied. A panelist uploading an ID will see nothing change.
2. **Minimum booking lead time is 3 days** (S13d), with no same-day or 1–2-day path, including for walk-ins. The paper's "1–2 days / same-day if a slot is open" contradicts what the date picker enforces on the first click.
3. **Booking statuses** (T1): the app shows Pending / Approved / In Progress / Completed / Cancelled. There is no "Scheduled" or "Rescheduled" status; rescheduling is a sub-state.
4. **Completion is not "upon payment"** (S5c): admin presses "Mark Completed" (or the report is submitted), with no payment check. Balance can be paid after completion.
5. **Cancellation lead-time policy does not exist** (S6a): anyone can cancel any time before completion, even mid-job. And same-day deduction has no fixed amount (S6c): admin types it in.
6. **Pricing is by unit type only** (S7b): no horsepower anywhere.
7. **Down payment / Down payment by service** (S7c, S7e): options are admin-editable (seeded 30/50/100); no "cleaning needs no DP" rule; Return customers get a 0% option (UI-only); leftover 10% fallbacks in code.
8. **VAT** (S7f): 12% is added automatically for Commercial clients only; there is no "on request" switch and residential clients can't get VAT.
9. **Distance charge** (S7i): not computed; admin types a number per booking; no rate table.
10. **Landing search** (S4a): date search not built; technician search shows each technician's individual reviews instead of a company-wide aggregate; footer phone number is a placeholder (S4c); landing page promises a "30-day warranty" while the real periods are 7 days / 6 months / 3 months / 1 month (S8a); landing stats ("4.9★", "500+ clients") are hardcoded.
11. **Dashboard/analytics are not graphical** (S18a): 4 stat cards + tables, no charts, no technician workload; "missed assignments" not built, "delays" = disruption/extension count, "average time" = self-entered labor hours (S21).
12. **Real-time monitoring** (S15): fetch-on-load only; the only polling is chat (15 s); the one automatic status change is a midnight cron (Approved → In Progress).
13. **Customer Classification** (S12a, S12b): rule is 3 completed bookings (any service, repeats count) in 12 months, not "3 different services"; the 0% DP perk is UI-only.
14. **Teams, lead/helper, multi-technician, solo-vs-pair rules** (S13b, S13f, S13g): none exist; one technician per booking; no auto-assignment (S13c); no reorder of pending requests (S5e); no promotional packages (S17c).
15. **Billing record** (S7a, S7j): no separate billing record or labor/materials breakdown; billing is a view over the booking; no corporate-specific itemization; free-warranty (back-job) bookings still show in admin Payments (S7l).
16. **Report consent/signature** (S16c): captured on the technician's device, customers never see or sign it in their own account; no dedicated "unit condition" field (S16b).
17. **Tech stack wording** (M1): MongoDB (Mongoose 9.7.4) only; Express 5.2.1; React 19.2.7 + Vite 8.1.0; JWT + bcryptjs; multer; node-cron; Bootstrap is *not* actually used.
18. **Problems a panelist can find in code or by poking** (not paper claims, but would hurt in defense): anyone can self-register as a technician; admin-created accounts keep plain-text passwords; login logs passwords to the console; deactivated accounts can still log in; reschedule approve/deny routes have no role check and the admin has no button for them; `/uploads` proofs are public; no route-level or frontend tests (22 server unit tests exist).
